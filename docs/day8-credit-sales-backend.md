Implemented on 2026-11-03. Frontend work remains Step 8.3.

## Audit findings and reuse

The Step 8.1 audit in the conversation identified working CreditAccount/LedgerEntry models, read-only effective ledger calculations, ownership checks, unique receipt/idempotency fields, and no sale recording endpoint. Reused those models, constraints, authentication dependencies, approved-business ownership helper, database session lifecycle, and Day 7 test fixtures. No alternate ledger or balance table was introduced.

Repeated balance calculations in customer details, customer list, credit-account management, and dashboard summary now use app/services/ledger_service.py. Reversal exclusion is account-scoped consistently; dashboard recent transactions use the same account scope. Ledger history is never rewritten by a sale.

## API contract

POST /api/v1/shop-owner/credit-sales?business_id=123

Authenticated Shop Owner access is required. Business ID remains a query parameter, matching existing customer endpoints.

Example JSON body (replace identifiers and create a new stable key for each intended sale):

```json
{
  "customer_id": 456,
  "amount": "1250.50",
  "notes": "Goods supplied on credit",
  "idempotency_key": "credit-sale:unique-client-request-id"
}
```

- customer_id: strict positive integer within signed BIGINT capacity.
- amount: positive finite Decimal, maximum 14 total digits and two decimal places. Decimal strings are recommended; financially equivalent trailing zeros compare equally.
- notes: optional, maximum 2000 characters; leading/trailing whitespace removed and blank normalized to null.
- idempotency_key: required, 1-100 ASCII characters; first character alphanumeric, remaining characters alphanumeric or `.`, `_`, `:`, `-`. Matching includes exact key spelling even when MySQL uses a case-insensitive collation.
- Unknown fields are rejected. Actor, account, entry type, dates, and receipt are server-controlled. This sale request does not accept payment methods or order IDs.

Response fields:

| Field | Meaning |
| --- | --- |
| entry_id | Original/new LedgerEntry ID |
| business_id, customer_id, credit_account_id | Authorized transaction scope |
| currency | LKR |
| amount | Two-decimal string |
| outstanding_balance, advance_balance, available_credit | Two-decimal strings calculated while holding the account lock |
| recorded_at | Existing server-generated transaction timestamp, serialized as ISO datetime |
| due_at | Recording timestamp plus the account payment-term days at creation |
| receipt_number, reference | Unique CS-prefixed reference generated by the server |
| notes | Normalized original notes |
| replayed | Whether this response reuses an existing transaction |

Status codes: 201 for a new sale; 200 for an identical successful replay; 401 for missing/invalid credentials; 403 for role, user, ownership, membership, or approval failure; 404 for a customer/account outside the selected business or missing; 409 for inactive account, exceeded credit, or conflicting idempotency details; 422 for invalid input or an account term that would overflow the supported due-date range. Database failures return a generic 500 without internal diagnostics.

## Financial and transaction behavior

1. Check approved business ownership using existing dependencies/helper.
2. Resolve the customer within that business.
3. Lock the matching CreditAccount using SELECT FOR UPDATE and refresh its ORM state.
4. Read originals and reversals with a current locking read. This avoids a stale repeatable-read snapshot established by earlier authentication queries.
5. Calculate effective balance using shared Decimal arithmetic.
6. Replay an identical operation or reject key reuse for a different account, type, amount, notes, or key spelling.
7. For a new operation, require active account status and amount <= available credit.
8. Insert a single sale, unique receipt reference, and due date. Commit only after all writes and response construction succeed; otherwise roll back.

Existing Day 7 behavior is preserved: outstanding=max(net balance,0), advance=max(-net balance,0), available=max(limit-outstanding,0). Advances reduce the resulting net debt but do not expand the permitted new sale amount above the account limit. Credit limits are never changed automatically.

Idempotency is enforced by both account serialization and the existing globally unique database index. A pre-insert SELECT is not treated as sufficient protection. Cross-account uniqueness races are rolled back and reevaluated in a fresh transaction. MySQL deadlocks/lock timeouts also trigger a bounded retry, with at most three attempts. Other SQL errors are rolled back and sanitized.

Replays return the original entry ID, receipt, and timestamps with the current effective balances. They do not create another sale, reinstate a reversed sale, or fail solely because the original successful operation's account is now suspended. Current business authorization is still required.

- One existing InsecureKeyLengthWarning remains in the tampered-token test's deliberately incorrect signing key.
- Test table row counts before/after focused and complete regression runs were unchanged in all seven checked tables.

Ordinary tests reuse rollback-isolated Day 7 fixtures. Four concurrency tests use actual independent API/database sessions, actual JWT authentication, and real MySQL row/index enforcement. A blocking connection holds the account locks until both requests attempt acquisition; tests verify the requests wait before releasing the locks. Outcomes cover jointly excessive sales, identical retries, differing payloads with one key, and a globally shared key across different accounts.

Independent connections cannot see uncommitted fixture seeds. Concurrency fixtures therefore commit unique records solely in lankapex_test_db, then remove only their exact fixture-owned entry/account/customer/membership/business/user IDs and verify cleanup. No development rows, database resets, schema operations, or historical user records are involved.

## Scope and remaining decisions

No migration was required or applied. No frontend changes, commit, or push were made. The pre-existing .gitignore edit is preserved.

Due dates use the existing database timestamp convention and snapshot current payment terms; backdating and timezone-policy changes are deferred. CS references are unique transaction identifiers, not a sequential legal receipt system or printable receipt feature. Receipt rendering, repayment policy, and reversal recording remain later Day 8 steps. The existing full-history balance reads are retained; pagination/aggregation optimization can follow when required by volume.
